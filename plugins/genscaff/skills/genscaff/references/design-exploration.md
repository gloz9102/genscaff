# Representative-Screen Design Comparison

Use for a new surface or major redesign with open visual direction. Information delivery is the primary purpose: all candidates remain subject to existing project, craft, spacing, background, typography, radius, and accessibility requirements. Exploration does not create exceptions to those rules.

## User choice and routing

- Default to comparing two candidates. State this early and offer a single-direction option while continuing project inspection and the shared contract; do not create an initial approval gate merely to use the default.
- Honor an explicit single-direction preference immediately and do not ask again. Build one direction and perform normal verification.
- Skip comparison for Quick, narrow fixes, accessibility-only or localization-only changes, locked reproduction, or an extension whose design system already determines the composition. A token system alone does not settle an otherwise open major redesign.
- If the user explicitly requests alternatives in an otherwise narrow task, bound the comparison to that scope rather than expanding the whole project.

## Controlled comparison

1. Choose one representative screen or coherent section containing the primary information and decision. Fix the brief or before-state invariants and permitted changes.
2. Share the same required copy, factual values, item count, data, interaction state, asset set, and desktop/mobile viewport sizes. Show the same semantic region in each capture. Do not favor one candidate with shortened copy, better data, omitted errors, or exclusive imagery. Explain any user-requested difference that makes the comparison non-equivalent.
3. Produce two rendered candidates using existing components and styling. Keep data and behavior shared where practical. Describe meaningful differences in at least two of composition, typography hierarchy, density, and media role; color changes alone do not constitute alternatives. These axes identify an experiment, not a beauty score or permission to violate craft rules.
4. Inspect both at desktop and mobile. Check required information, accessible names, meaningful reading/focus sequence, clipping, and the representative primary action. Clearly identify prototype boundaries; comparison evidence is not whole-product verification.
5. Present A and B with viewable evidence, information-delivery tradeoffs, and a recommendation. Mark any failing candidate as needing repair; visual preference cannot waive a required invariant, functional, or accessibility failure.
6. Ask the user to select A, B, a specific combination, or a revision. Wait before expanding one candidate across the product unless the user explicitly delegated selection. Silence and elapsed time are not selection. Continue only common work independent of that decision while waiting.
7. Record the user's choice or delegated decision and implement it. A requested combination is a changed direction whose affected invariants and behavior need rechecking.

## Boundaries and evidence

Compare one pair by default, not two complete products. Do not add a permanent theme switcher, a second styling system, a dependency, or extra routes solely to support comparison. Keep temporary artifacts isolated from production output.

Candidate comparison is one bounded stage, separate from the selected implementation's first-render and one batched aesthetic recheck. Do not restart comparison without a changed user brief or request. Content, functionality, accessibility, and runtime defect fixes always require relevant re-verification regardless of aesthetic-pass limits.

If browser evidence is unavailable, continue shared implementation and retain two comparable direction descriptions and any available candidate source, clearly marked unverified, before a user or delegated selection. Missing rendering does not silently change the default to a single direction. Present available evidence and the limitation; do not fabricate screenshots, silently select a candidate, or award a verified status. The user may select an unverified direction with that limitation disclosed.

Record mode, shared inputs, candidate locations, differences, captures and observations, failures, user choice or delegation, and limitations in the human-readable contract. Candidate preference never raises the existing technical verification status.
