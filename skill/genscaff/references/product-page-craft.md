# Product-Page Craft

Use this after `task-type-craft-router.md` selects Product / commerce. Evaluate
the rendered desktop and mobile screenshots, plus the primary buy flow. Preserve
the product's actual category, price model, and existing brand evidence.

## Product checks

| Area | Screenshot or flow must show |
| --- | --- |
| Hero comprehension | The product, its use or result, and a next step are understandable in the first viewport. |
| Product visual quality | Product imagery or representation makes shape, material, scale, feature, or use legible; it is not generic decoration. |
| Option and price consequence | Selecting an option makes its availability, included items, price, delivery timing, or other decision consequence clear. |
| Merchandising and trust | Relevant proof such as stock, compatibility, shipping, returns, warranty, reviews, or limits appears near the decision without invented claims. |
| Conversion flow | The primary CTA leads to visible feedback, a purchase/cart result, and a recovery path such as remove, edit, or return. |
| Mobile CTA proximity | On a phone, price/selection context and the primary CTA remain reachable together without an excessive scroll or unclear state. |

## Visual outcome gate

For each item, mark `pass` or `revise` from the captured result and cite the
specific viewport/state that supports it. Do not infer a pass from source code.

| Outcome | Pass when |
| --- | --- |
| Composition | The first viewport has a clear visual anchor and intentional balance; supporting material does not compete with the purchase decision. |
| Product storytelling | Visuals and copy explain why this product exists or differs, not merely its name and a generic claim. |
| Hierarchy | Product, key value, price/decision, and CTA scan in a clear order at each viewport. |
| Brand coherence | Typography, color, imagery, surfaces, and interaction feedback feel like one deliberate system and match available project evidence. |
| Interaction polish | Selection, validation, loading, success, and recovery feedback make the next state obvious without layout breakage. |

If every outcome passes, stop. If any outcome needs revision, make a targeted
change tied to the failed screenshot evidence, recapture the affected viewport
and flow, then judge again. Allow at most two targeted iterations. If a failure
remains, report it plainly with the evidence instead of broad restyling or
claiming completion.

Do not reject gradients, glass, blur, glow, or similar effects merely for being
present. Revise them only when they lack user/project/reference support or
obscure product comprehension, trust, hierarchy, or action feedback.
