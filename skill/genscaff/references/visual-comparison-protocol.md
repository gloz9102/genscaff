# Visual Comparison Protocol

Use this Strict protocol after the implementation and primary flow exist. Do not load legacy brand or AI-slop research files merely to satisfy this protocol.

## Before capture

1. Record the user, task, success outcome, domain objects, primary CTA, recovery, and explicit constraints.
2. Record the existing design-system or locked-reference evidence that must be preserved.
3. Select the routed page-type craft reference and `workflow-rubric.md`.
4. Record required decisions, actions to success, and any justified initial disabled state.

## Evidence pass

- Capture distinct desktop and mobile start, feedback, terminal, recovery, and focus states.
- Exercise every visible control and reconcile the runtime inventory.
- Verify product or domain specificity, claim provenance, action continuity, recovery, keyboard operation, focus visibility, overflow, console state, and relevant long content.
- Run source, computed-style, SVG/canvas, raster, network, and Lighthouse checks defined by the Strict gate.
- Score functional completeness, efficiency, project fit, visual hierarchy, and responsive/accessibility basics from 0 to 5.
- Fail broken requirements, invented claims, undisclosed dead controls, missing recovery, or `FABRICATED_FRICTION` before considering scores.

## Iteration

Run two evidence-backed passes. Revise only failed hard gates or rubric dimensions below 3. Each change must name the finding it resolves and produce a new affected-state capture. Do not restyle passing areas to manufacture a second iteration.

## Independent review

Give a fresh reviewer only the brief, rendered captures, and action traces. Do not provide the implementer's diagnosis or desired verdict. Store the raw response and verify reviewer provenance separately from machine validation.

Lighthouse and automated accessibility results are technical evidence, not representative-user success or complete accessibility conformance.
